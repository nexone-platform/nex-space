# NexSpace — สิ่งที่มีตอนนี้ เทียบกับ Gather Town และสิ่งที่ต้องทำต่อ

> อัปเดต 19 ส.ค. 2026 · อ้างอิงจากโค้ดจริง (P0-1 เสร็จหลังจากนั้น)
> เอกสารนี้ใช้เป็นทั้งบันทึกสถานะและรายการงาน — แต่ละหัวข้อในส่วน "งานที่ต้องทำ" ตัดไปเป็น task ได้เลย

## สรุปย่อ

NexSpace **มีแกนกลางของ Gather ครบแล้ว**: โลกแบบเดินได้, คุยกันตามระยะใกล้, เสียง/ภาพ/แชร์จอ, ห้องประชุม, สิทธิ์และการเชิญ  บางเรื่องยัง **ทำได้ดีกว่า** Gather ด้วยซ้ำ (2FA ในตัว, ระบบบัตรแขกที่ตั้งวันหมดอายุและเพิกถอนได้, ไทย/อังกฤษเต็มระบบ)

ที่ยังขาดแบ่งได้เป็นสองกอง และสองกองนี้ต่างกันมาก:

1. **กองที่ทำให้ของที่มีอยู่ "ใช้จริงในองค์กรได้"** — TURN server, SFU, SMTP, ประวัติแชท  ของพวกนี้ไม่ใช่ฟีเจอร์ใหม่ แต่เป็นเงื่อนไขที่ทำให้ฟีเจอร์ที่เขียนเสร็จแล้วไม่พังในสภาพแวดล้อมจริง **ควรทำก่อนอย่างอื่นทั้งหมด**
2. **กองที่เป็นฟีเจอร์ Gather ที่เรายังไม่มี** — Mapmaker, พื้นที่ส่วนตัว, ปฏิทิน, บันทึกการประชุม, มือถือ

## ส่วนที่ 2 — งานที่ต้องทำ เรียงตามลำดับที่ควรทำ

ขนาดงาน: **S** = 1–2 วัน · **M** = 3–5 วัน · **L** = 1–2 สัปดาห์ · **XL** = มากกว่านั้น

### P0 — ทำให้ของที่มีอยู่ใช้ได้จริง (ต้องทำก่อน)

**P0-1 · TURN server** — ✅ **โค้ดเสร็จแล้ว รอตั้งค่าบนเซิร์ฟเวอร์**
เดิมมีแค่ STUN ของ Google ผู้ใช้หลัง NAT เข้มงวดหรือไฟร์วอลล์บริษัท (คือกลุ่มเป้าหมายของเรา) **เชื่อมเสียงไม่ติดเลยและไม่มีข้อความบอกว่าทำไม**
ตอนนี้มี coturn ใน compose (เปิดด้วย `--profile turn`), `/ice` ออก credential อายุสั้นให้ทั้งสมาชิกและแขกที่ถือบัตร, เบราว์เซอร์ดึงมาใช้เองและมีสิทธิ์ restart ICE หนึ่งครั้ง
เหลือ **งานบนเซิร์ฟเวอร์**: ตั้ง `TURN_SECRET`/`TURN_HOST` ใน `.env`, เปิดพอร์ต 3478 กับ 49160–49260/udp, แล้วพิสูจน์ด้วย `node scripts/turn-check.mjs` จากเครื่องอื่น (ดู DEPLOY.md)

**P0-2 · เปลี่ยนไปใช้ SFU (LiveKit)** — `L` — *ไฟล์: `apps/web/src/net/livekit.ts` (เขียนไว้แล้ว), `docker-compose.yml:30`*
ตอนนี้เป็น P2P mesh: ทุกคนส่งสายตรงหากันทุกคน  ที่ 8 คนคือ 56 สาย เครื่องผู้ใช้เริ่มไม่ไหว **เพดานจริงอยู่ราว 6–8 คนต่อกลุ่ม** ตัวเชื่อม LiveKit เขียนเสร็จแล้วและ compose มีตัวแปรรออยู่ เหลือแค่ตั้งเซิร์ฟเวอร์, ออก token จาก API, และสลับ adapter  ถ้าจะขายให้ทีม 20+ คน ข้อนี้บังคับ

**P0-3 · SMTP** — ⚙️ **ไม่ใช่งานเขียนโค้ด เป็นงานตั้งค่า**
`apps/api/src/mailer.ts` ส่งอีเมลได้ครบแล้ว (nodemailer + เทมเพลตภาษาไทย) แค่ยังไม่มีค่า `SMTP_*` ใน `.env` บนเซิร์ฟเวอร์ รหัสจึงตกไปอยู่ใน log ตามที่ตั้งใจไว้เมื่อไม่ได้ตั้งค่า
ใส่ค่าตาม DEPLOY.md แล้วเสร็จทันที — และ P1-3 (เชิญทางอีเมล) ถึงจะเริ่มได้

**P0-4 · เก็บประวัติแชท** — ✅ **เสร็จแล้ว**
มีตาราง `Message`, game server บันทึกให้ในนามคนพูด (ใช้ credential เดิมที่เปิดประตูห้อง จึงไม่ต้องเพิ่มความลับใหม่), เบราว์เซอร์โหลด 50 ข้อความล่าสุดตอนเข้าห้องพร้อมเส้นคั่น "ก่อนหน้านี้", และกวาดทิ้งอัตโนมัติตาม `CHAT_KEEP_DAYS` (ค่าเริ่มต้น 90 วัน)
สิทธิ์การอ่านผูกกับประตูเดียวกับห้อง — สมาชิกหรือบัตรแขกที่ยังไม่หมดอายุ · ทดสอบ 31 ข้อ รวมเส้นทางผ่าน socket จริง

### P1 — ฟีเจอร์ที่ผู้ใช้ Gather คาดว่าต้องมี

**P1-1 · พื้นที่ส่วนตัว (Private Area)** — `M` — *ไฟล์: `apps/web/src/scenes/mapThemes.ts`, `OfficeScene.ts` (ตรรกะ proximity บรรทัด ~2181)*
Gather ใช้กันหนักที่สุดรองจากการเดิน: ยืนในโซนเดียวกัน = ได้ยินเฉพาะคนในโซน คนนอกไม่ได้ยินและแทรกไม่ได้  ของเรามีแค่รัศมีรอบตัวกับห้องประชุมทั้งห้อง ทำให้ "จับกลุ่มคุยงานเล็ก ๆ ข้างโต๊ะ" ยังทำไม่ได้ ตรรกะเสียงมีอยู่แล้ว เพิ่มเป็นเงื่อนไข "โซนเดียวกันเหนือกว่าระยะทาง"

**P1-2 · ข้อความส่วนตัว (DM) 1:1** — ✅ **เสร็จแล้ว**
เข้าจากรายชื่อคน (ปุ่มโผล่เมื่อชี้) มีหน้ารายการสนทนาพร้อมจำนวนที่ยังไม่อ่าน และป้ายรวมบนแถบซ้าย
ส่งถึงกันสดผ่าน socket และเก็บลงฐานข้อมูลเสมอ — ข้อความส่วนตัวมีไว้เพื่อรอคนที่ไม่ได้อยู่ตรงนั้น
ต้องมีบัญชีทั้งสองฝั่งและอยู่ workspace เดียวกัน (แขกใช้ห้องรวมแทน) · ตัวนับที่ยังไม่อ่านเก็บฝั่งเซิร์ฟเวอร์ อ่านบนมือถือแล้วเดสก์ท็อปก็หาย
**ทดสอบ 30 ข้อ** ข้อสำคัญที่สุดคือข้อความส่วนตัวต้องไม่โผล่ในประวัติห้อง — ตรวจทั้งมุมคนส่ง คนอื่นในห้อง และแขก

**P1-3 · เชิญทางอีเมล + สถานะ "เชิญแล้วรอตอบรับ"** — `M` — *ไฟล์: `apps/api/src/index.ts`, `memberPanel.ts`*
แท็บ "คำเชิญ" ในหน้าจัดการสมาชิกยังเป็นที่ว่างรออยู่ ต้องรอ P0-3

**P1-4 · ตามตัว / เรียกคน** — ✅ **เสร็จแล้ว**
"ตามตัว" ส่งกล้องไปตามคนนั้นจนกว่าจะเดินเอง (ใช้สถานะเดียวกับการลากแผนที่) ถ้าเขาออกจากห้องกล้องกลับมาเอง
"เรียกมาหา" เป็น**คำเชิญ ไม่ใช่คำสั่ง** — ปลายทางกดรับเองเท่านั้น และจำกัดความถี่ต่อคู่ เพราะปุ่มที่ย้ายคนอื่นได้คือปุ่มที่คนกดสิบสองครั้ง · ไปถึงแล้วยืนข้าง ๆ ไม่ใช่ทับตัว

**P1-5 · ศูนย์การแจ้งเตือน + เสียงเตือน** — ✅ **เสร็จแล้ว**
กระดิ่งบนแถบซ้ายพร้อมรายการสิ่งที่พลาดไป กดที่รายการแล้วพาไปยังที่นั้น (ข้อความส่วนตัว / คนเรียกให้ไปหา)
เสียงเตือนสร้างจาก oscillator ไม่ใช่ไฟล์เสียง — ไม่มี asset ไม่มีการโหลด ไม่มีลิขสิทธิ์ให้ตาม และไม่มีวันมาช้า · ปิดได้ที่หัวรายการ

**P1-6 · โหมดห้ามรบกวน** — ✅ **เสร็จแล้ว**
ปุ่มเดียวในแถบล่าง สามผลพร้อมกัน: คนรอบตัวเงียบ, เสียงแจ้งเตือนหยุด, และใครที่กดเรียกจะได้รับแจ้งว่ากำลังห้ามรบกวน
กฎอยู่ที่**เซิร์ฟเวอร์** ไม่ใช่แค่ปิดเสียงในแท็บตัวเอง — ไม่งั้นคนที่กดเรียกจะไม่มีทางรู้ว่าคำขอไปไม่ถึง
**ไม่แตะไมค์ของคุณ** เพราะการเปลี่ยนสถานะไมค์ลับหลังคือสาเหตุที่คนพูดกับความว่างเปล่า · สายเสียงยังต่ออยู่แค่ปิดเสียง เปิดกลับจึงทันที และอีกฝ่ายไม่มีทางรู้ว่าถูกปิดเสียง · ทดสอบ 11 ข้อผ่าน socket จริง

**P1-7 · รองรับมือถือ/แท็บเล็ต** — `L`
เลย์เอาต์ใหม่ยุบเป็นช่องเดียวเมื่อจอแคบกว่า 760px แล้ว แต่ยังไม่มีปุ่มบังคับทิศทางแบบสัมผัส และยังไม่เคยทดสอบบนเครื่องจริง

**P1-8 · โปรไฟล์ผู้ใช้** — ✅ **เสร็จแล้ว**
คลิกชื่อในรายชื่อ → การ์ดโปรไฟล์ (แนะนำตัว, ทีม, เขตเวลาพร้อมเวลาจริงของเขาตอนนี้) และเป็นที่รวมปุ่มข้อความ/ตามตัว/เรียกมาหา
การ์ดของตัวเองคือฟอร์มแก้ไข — โปรไฟล์ที่ซ่อนอยู่หลังหน้าตั้งค่าคือโปรไฟล์ที่ไม่มีใครกรอก
อ่านการ์ดของใครได้เพราะ**อยู่พื้นที่เดียวกัน** ไม่ใช่เพราะรู้รหัสบัญชี · ทดสอบ 17 ข้อ

### P2 — ตัวคูณระยะยาว

**P2-1 · Mapmaker** — `XL` — *ฐานมีอยู่แล้ว: `SavedMap` ใน Prisma + `/maps` ใน API แต่ยังไม่มีหน้าจอ และ scene ยังโหลดธีมจากโค้ด*
นี่คือฟีเจอร์ที่ทำให้ Gather เป็น Gather: ลูกค้าสร้างออฟฟิศของตัวเองได้โดยไม่ต้องรอเรา ตอนนี้ลูกค้าเลือกได้แค่ 3 ธีมที่เราเขียนไว้  งานใหญ่ที่สุดในเอกสารนี้ และควรแตกเป็นหลาย task: วางพื้น → วางพร็อพ → กำแพง/สิ่งกีดขวาง → จุดเกิด → พื้นที่ส่วนตัว → วัตถุโต้ตอบ

**P2-2 · หลายแผนที่ต่อพื้นที่ (ชั้น/อาคาร)** — `L`
ตอนนี้หนึ่งพื้นที่ = หนึ่งแผนที่ ประตูมิติข้ามได้แค่ภายในแผนที่เดียวกัน

**P2-3 · ปฏิทินและนัดหมาย** — `L`

**P2-4 · บันทึกการประชุม** — `L`

**P2-5 · เคาะประตู (Knock)** — `S`
ห้องส่วนตัวที่ล็อกอยู่ ผู้มาเยือนเคาะ เจ้าของกดรับ ต่อยอดจาก P1-1

**P2-6 · แดชบอร์ดผู้ดูแล** — `M`
ใครเข้าออกเมื่อไหร่, ใช้งานกี่ชั่วโมง, ห้องไหนถูกใช้บ่อย

**P2-7 · SSO / SAML + ผูก Google Workspace** — `L`

**P2-8 · API สาธารณะ / webhook / บอท** — `L`

**P2-9 · ส่งไฟล์และรูปในแชท** — `M`

**P2-10 · ท่าทางอวตาร (โบกมือ, เต้น) และสติกเกอร์บนแผนที่** — `S`

## ส่วนที่ 3 — ข้อจำกัดเชิงสถาปัตยกรรมที่ควรตัดสินใจก่อนลงมือ P1

เรื่องเหล่านี้ไม่ใช่ "ฟีเจอร์" แต่ถ้าตัดสินใจช้าจะต้องรื้องานที่ทำไปแล้ว

1. **P2P mesh กับ SFU** — ทุกฟีเจอร์เกี่ยวกับเสียง/ภาพ (บันทึกการประชุม, พื้นที่ส่วนตัว, ห้องใหญ่) ตั้งอยู่บนคำตอบข้อนี้ ควรตัดสินใจก่อนเขียนโค้ดสื่อสารเพิ่ม
2. **SQLite** — ตอนนี้ทั้งระบบอยู่บนไฟล์เดียว เขียนพร้อมกันได้ทีละราย ยังพอไหวสำหรับหลักสิบคน แต่ประวัติแชท (P0-4) และแดชบอร์ด (P2-6) จะเป็นตัวเร่งให้ต้องย้ายไป Postgres
3. **หนึ่งห้อง Colyseus ต่อหนึ่งพื้นที่** (`OfficeRoom` ตั้ง `autoDispose = false`) — แปลว่าทุกคนในพื้นที่อยู่ในโปรเซสเดียว ขยายข้ามเครื่องไม่ได้จนกว่าจะใส่ Redis presence
4. **แผนที่อยู่ในโค้ดฝั่งเบราว์เซอร์** — `mapThemes.ts` ถูกคอมไพล์ไปกับตัวเว็บ ตราบใดที่ยังเป็นแบบนี้ Mapmaker (P2-1) เกิดไม่ได้ ต้องย้ายไปโหลดแผนที่จาก API ตอนรันก่อน ซึ่งเป็นงานที่ทำแยกไปก่อนได้เลยและควรทำก่อน P2-1

## ลำดับที่แนะนำ

```
สัปดาห์ 1     P0-3 (ใส่ค่า SMTP) + P0-1 (ตั้ง TURN บนเซิร์ฟเวอร์ แล้ว turn-check)
สัปดาห์ 3–4   P0-2 (SFU) — พร้อมทดสอบโหลดจริง 10+ คน  ⚠️ ต้องการเครื่องที่รับ UDP ได้เหมือน TURN
สัปดาห์ 5–6   P1-1 (พื้นที่ส่วนตัว) เหลือข้อเดียวใน P1 ที่ยังไม่ติดโครงสร้างพื้นฐาน
              ·  P1-2 DM, P1-4 ตามตัว, P1-5 แจ้งเตือน, P1-8 โปรไฟล์ เสร็จแล้ว
สัปดาห์ 7–8   P1-3 (เชิญทางอีเมล) → ย้ายแผนที่ออกจากโค้ด (เตรียม Mapmaker)
ต่อจากนั้น    P2-1 Mapmaker เป็นสายงานหลัก, P1-7 มือถือ เป็นสายงานคู่ขนาน
```

เหตุผลของลำดับนี้: **P0 ทุกข้อคือสิ่งที่ทำให้ผู้ใช้เจอปัญหาโดยที่เราไม่รู้ตัว** (เสียงไม่ติดเพราะไม่มี TURN, ข้อความหาย, อีเมลไม่ถึง) ส่วน P1 คือสิ่งที่ผู้ใช้จะบอกเราเองว่าขาด และ P2 คือสิ่งที่ตัดสินว่าเราขายเป็นสินค้าได้หรือทำได้แค่พื้นที่เดียวให้ทีมเดียว
