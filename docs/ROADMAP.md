# NexSpace — สิ่งที่มีตอนนี้ เทียบกับ Gather Town และสิ่งที่ต้องทำต่อ

> อัปเดต 19 ส.ค. 2026 · อ้างอิงจากโค้ดจริง (P0-1 เสร็จหลังจากนั้น)
> เอกสารนี้ใช้เป็นทั้งบันทึกสถานะและรายการงาน — แต่ละหัวข้อในส่วน "งานที่ต้องทำ" ตัดไปเป็น task ได้เลย

## สรุปย่อ

NexSpace **มีแกนกลางของ Gather ครบแล้ว**: โลกแบบเดินได้, คุยกันตามระยะใกล้, เสียง/ภาพ/แชร์จอ, ห้องประชุม, สิทธิ์และการเชิญ  บางเรื่องยัง **ทำได้ดีกว่า** Gather ด้วยซ้ำ (2FA ในตัว, ระบบบัตรแขกที่ตั้งวันหมดอายุและเพิกถอนได้, ไทย/อังกฤษเต็มระบบ)

ที่ยังขาดแบ่งได้เป็นสองกอง และสองกองนี้ต่างกันมาก:

1. **กองที่ทำให้ของที่มีอยู่ "ใช้จริงในองค์กรได้"** — TURN server, SFU, SMTP, ประวัติแชท  ของพวกนี้ไม่ใช่ฟีเจอร์ใหม่ แต่เป็นเงื่อนไขที่ทำให้ฟีเจอร์ที่เขียนเสร็จแล้วไม่พังในสภาพแวดล้อมจริง **ควรทำก่อนอย่างอื่นทั้งหมด**
2. **กองที่เป็นฟีเจอร์ Gather ที่เรายังไม่มี** — ปฏิทิน, บันทึกการประชุม, มือถือ

## ส่วนที่ 2 — งานที่ต้องทำ เรียงตามลำดับที่ควรทำ

ขนาดงาน: **S** = 1–2 วัน · **M** = 3–5 วัน · **L** = 1–2 สัปดาห์ · **XL** = มากกว่านั้น

### P0 — ทำให้ของที่มีอยู่ใช้ได้จริง (ต้องทำก่อน)

**P0-1 · TURN server** — ✅ **โค้ดเสร็จแล้ว รอตั้งค่าบนเซิร์ฟเวอร์**
เดิมมีแค่ STUN ของ Google ผู้ใช้หลัง NAT เข้มงวดหรือไฟร์วอลล์บริษัท (คือกลุ่มเป้าหมายของเรา) **เชื่อมเสียงไม่ติดเลยและไม่มีข้อความบอกว่าทำไม**
ตอนนี้มี coturn ใน compose (เปิดด้วย `--profile turn`), `/ice` ออก credential อายุสั้นให้ทั้งสมาชิกและแขกที่ถือบัตร, เบราว์เซอร์ดึงมาใช้เองและมีสิทธิ์ restart ICE หนึ่งครั้ง
เหลือ **งานบนเซิร์ฟเวอร์**: ตั้ง `TURN_SECRET`/`TURN_HOST` ใน `.env`, เปิดพอร์ต 3478 กับ 49160–49260/udp, แล้วพิสูจน์ด้วย `node scripts/turn-check.mjs` จากเครื่องอื่น (ดู DEPLOY.md)

**P0-2 · เปลี่ยนไปใช้ SFU (LiveKit)** — `L` — *ไฟล์: `apps/web/src/net/livekit.ts` (เขียนไว้แล้ว), `docker-compose.yml:30`*
ตอนนี้เป็น P2P mesh: ทุกคนส่งสายตรงหากันทุกคน  ที่ 8 คนคือ 56 สาย เครื่องผู้ใช้เริ่มไม่ไหว **เพดานจริงอยู่ราว 6–8 คนต่อกลุ่ม** ตัวเชื่อม LiveKit เขียนเสร็จแล้วและ compose มีตัวแปรรออยู่ เหลือแค่ตั้งเซิร์ฟเวอร์, ออก token จาก API, และสลับ adapter  ถ้าจะขายให้ทีม 20+ คน ข้อนี้บังคับ

**P0-3 · SMTP** — ⚙️ **ไม่ใช่งานเขียนโค้ด เป็นงานตั้งค่า**
`apps/api/src/mailer.ts` ส่งอีเมลได้ครบแล้ว (nodemailer + เทมเพลตภาษาไทย) แค่ยังไม่มีค่า `SMTP_*` ใน `.env` บนเซิร์ฟเวอร์ รหัสจึงตกไปอยู่ใน log ตามที่ตั้งใจไว้เมื่อไม่ได้ตั้งค่า
ใส่ค่าตาม DEPLOY.md แล้วเสร็จทันที — และ P1-3 (เชิญทางอีเมล) ถึงจะเริ่มได้

**P0-4 · เก็บประวัติแชท** — ✅ **เสร็จแล้ว**
มีตาราง `Message`, game server บันทึกให้ในนามคนพูด (ใช้ credential เดิมที่เปิดประตูห้อง จึงไม่ต้องเพิ่มความลับใหม่), เบราว์เซอร์โหลด 50 ข้อความล่าสุดตอนเข้าห้องพร้อมเส้นคั่น "ก่อนหน้านี้", และกวาดทิ้งอัตโนมัติตาม `CHAT_KEEP_DAYS` (ค่าเริ่มต้น 90 วัน)
สิทธิ์การอ่านผูกกับประตูเดียวกับห้อง — สมาชิกหรือบัตรแขกที่ยังไม่หมดอายุ · ทดสอบ 31 ข้อ รวมเส้นทางผ่าน socket จริง

### P1 — ฟีเจอร์ที่ผู้ใช้ Gather คาดว่าต้องมี

**P1-1 · พื้นที่ส่วนตัว (Private Area)** — ✅ **เสร็จแล้ว**
ยืนในโซนเดียวกัน = ได้ยินกันหมดไม่ว่าอยู่ไกลแค่ไหน และคนนอกไม่ได้ยินเลย แม้ยืนห่างแค่ช่องเดียวถัดจากเส้น  กฎเดียวกันนี้คุมทั้งเสียง (เบราว์เซอร์) และข้อความตามระยะ (เซิร์ฟเวอร์)
14 โซนใน 3 แผนที่ — ห้องประชุม ห้องแผนก ห้องครัว โซนพักผ่อน ห้องเกม  พื้นที่เปิดโล่งตรงกลางตั้งใจไม่เป็นโซน ไม่งั้นแผนที่จะไม่เหลือที่สาธารณะ
วาดกรอบและป้ายชื่อไว้บนแผนที่ พร้อมป้ายบอกโซนที่กำลังยืนอยู่ — กฎที่มองไม่เห็นคือกฎที่คนคิดว่าระบบพัง  คนที่ไม่ได้ยินเราจะถูกวาดจาง ๆ
ตารางโซนถูกคัดลอกไว้สองที่ (เว็บกับ game server สร้างคนละ Docker context จึง import ข้ามกันไม่ได้) — `scripts/areas-check.mjs` ทำให้บิลด์ล้มถ้าสองสำเนาไม่ตรงกัน
**ทดสอบ 10 ข้อผ่านซ็อกเก็ตจริง** ข้อสำคัญที่สุดคือคนที่ยืนห่างประตูหนึ่งช่องต้องไม่ได้ยิน — ปิดกฎแล้วเทสต์ล้ม 7 จาก 10

**P1-2 · ข้อความส่วนตัว (DM) 1:1** — ✅ **เสร็จแล้ว**
เข้าจากรายชื่อคน (ปุ่มโผล่เมื่อชี้) มีหน้ารายการสนทนาพร้อมจำนวนที่ยังไม่อ่าน และป้ายรวมบนแถบซ้าย
ส่งถึงกันสดผ่าน socket และเก็บลงฐานข้อมูลเสมอ — ข้อความส่วนตัวมีไว้เพื่อรอคนที่ไม่ได้อยู่ตรงนั้น
ต้องมีบัญชีทั้งสองฝั่งและอยู่ workspace เดียวกัน (แขกใช้ห้องรวมแทน) · ตัวนับที่ยังไม่อ่านเก็บฝั่งเซิร์ฟเวอร์ อ่านบนมือถือแล้วเดสก์ท็อปก็หาย
**ทดสอบ 30 ข้อ** ข้อสำคัญที่สุดคือข้อความส่วนตัวต้องไม่โผล่ในประวัติห้อง — ตรวจทั้งมุมคนส่ง คนอื่นในห้อง และแขก

**P1-3 · เชิญทางอีเมล + สถานะ "เชิญแล้วรอตอบรับ"** — `M` — *ไฟล์: `apps/api/src/index.ts`, `memberPanel.ts`*
แท็บ "คำเชิญ" ในหน้าจัดการสมาชิกยังเป็นที่ว่างรออยู่ ต้องรอ P0-3

**P1-4 · ตามตัว / เรียกคน** — ✅ **เสร็จแล้ว**
"ตามตัว" ส่งกล้องไปตามคนนั้นจนกว่าจะเดินเอง (ใช้สถานะเดียวกับการลากแผนที่) ถ้าเขาออกจากห้องกล้องกลับมาเอง
"เรียกมาหา" เป็น**คำเชิญ ไม่ใช่คำสั่ง** — ปลายทางกดรับเองเท่านั้น และจำกัดความถี่ต่อคู่ เพราะปุ่มที่ย้ายคนอื่นได้คือปุ่มที่คนกดสิบสองครั้ง · ไปถึงแล้วยืนข้าง ๆ ไม่ใช่ทับตัว

**P1-5 · ศูนย์การแจ้งเตือน + เสียงเตือน** — ✅ **เสร็จแล้ว**
กระดิ่งบนแถบซ้ายพร้อมรายการสิ่งที่พลาดไป กดที่รายการแล้วพาไปยังที่นั้น (ข้อความส่วนตัว / คนเรียกให้ไปหา)
เสียงเตือนสร้างจาก oscillator ไม่ใช่ไฟล์เสียง — ไม่มี asset ไม่มีการโหลด ไม่มีลิขสิทธิ์ให้ตาม และไม่มีวันมาช้า · ปิดได้ที่หัวรายการ

**P1-6 · โหมดห้ามรบกวน** — ✅ **เสร็จแล้ว**
ปุ่มเดียวในแถบล่าง สามผลพร้อมกัน: คนรอบตัวเงียบ, เสียงแจ้งเตือนหยุด, และใครที่กดเรียกจะได้รับแจ้งว่ากำลังห้ามรบกวน
กฎอยู่ที่**เซิร์ฟเวอร์** ไม่ใช่แค่ปิดเสียงในแท็บตัวเอง — ไม่งั้นคนที่กดเรียกจะไม่มีทางรู้ว่าคำขอไปไม่ถึง
**ไม่แตะไมค์ของคุณ** เพราะการเปลี่ยนสถานะไมค์ลับหลังคือสาเหตุที่คนพูดกับความว่างเปล่า · สายเสียงยังต่ออยู่แค่ปิดเสียง เปิดกลับจึงทันที และอีกฝ่ายไม่มีทางรู้ว่าถูกปิดเสียง · ทดสอบ 11 ข้อผ่าน socket จริง

**P1-7 · รองรับมือถือ/แท็บเล็ต** — `L`
เลย์เอาต์ใหม่ยุบเป็นช่องเดียวเมื่อจอแคบกว่า 760px แล้ว แต่ยังไม่มีปุ่มบังคับทิศทางแบบสัมผัส และยังไม่เคยทดสอบบนเครื่องจริง

**P1-8 · โปรไฟล์ผู้ใช้** — ✅ **เสร็จแล้ว**
คลิกชื่อในรายชื่อ → การ์ดโปรไฟล์ (แนะนำตัว, ทีม, เขตเวลาพร้อมเวลาจริงของเขาตอนนี้) และเป็นที่รวมปุ่มข้อความ/ตามตัว/เรียกมาหา
การ์ดของตัวเองคือฟอร์มแก้ไข — โปรไฟล์ที่ซ่อนอยู่หลังหน้าตั้งค่าคือโปรไฟล์ที่ไม่มีใครกรอก

**P2-1 · Mapmaker** — ✅ **เสร็จแล้ว**
นี่คือฟีเจอร์ที่ทำให้ Gather เป็น Gather: ลูกค้าสร้างออฟฟิศของตัวเองได้โดยไม่ต้องรอเรา

**รูปแบบไฟล์ — แผนที่ไม่ได้อยู่ในโค้ดอีกต่อไป** (ดูข้อจำกัดข้อ 4 ที่ปิดไปแล้ว)
รูปแบบไฟล์ `MapDoc` v1 (`mapValidate.ts`) — `floorAt()` กับ `walls()` กลายเป็นตารางตัวเลขกับรายการพิกัด ซึ่งเป็นรูปที่เครื่องมือวาดผลิตได้ด้วยการคลิก และพาโค้ดเข้าเบราว์เซอร์ไม่ได้แบบที่ฟังก์ชันที่เก็บไว้ทำได้
ทั้ง 3 ธีมแปลงกลับไปกลับมาได้ตรงทุกช่องพื้นและทุกกำแพง ประมาณ 6 KB ต่อธีม
`GET/PUT/DELETE /workspaces/:slug/map` — อ่านได้เท่าที่เห็นพื้นที่ เขียนได้เฉพาะ owner/admin · ตรวจความถูกต้องทั้งสองฝั่ง เพราะแผนที่หนึ่งใบถึงทุกเบราว์เซอร์ในพื้นที่พร้อมกัน
เบราว์เซอร์โหลดแผนที่ก่อนสร้างฉาก — การเดาจาก localStorage แล้วรีโหลดแก้ทีหลังหายไปแล้ว · game server อ่าน endpoint เดียวกัน โซนส่วนตัวของแผนที่ที่ทำเองจึงบังคับใช้จริงทั้งเสียงและข้อความ
**ทดสอบ 34 ข้อ**

**หน้าจอวาด** — `/editor.html?w=<slug>` เข้าจากหน้าตั้งค่า Space (เห็นเฉพาะ owner/admin)
เครื่องมือ 8 ชิ้นครบตามที่วางไว้: พื้น · กำแพง · พร็อพ · โต๊ะ · โซนส่วนตัว · จุดเกิด · วัตถุโต้ตอบ · ลบ

วาดด้วยตัวเรนเดอร์ตัวเดียวกับที่หน้าเลือกธีมใช้ ซึ่งลอกกฎการวางของฉากจริง — เครื่องมือที่วาดด้วยตรรกะของตัวเองคือเครื่องมือที่โกหกเรื่องที่เราเปิดมันมาจัดพอดี
ตรวจความถูกต้องแบบสด ไม่ใช่ตอนกดบันทึก: แถบล่างบอกเหตุผลที่แผนที่จะถูกปฏิเสธ และปุ่มบันทึกกดไม่ได้จนกว่าจะแก้
เลิกทำยุบการลากหนึ่งครั้งเป็นหนึ่งขั้น · รายการพร็อพสร้างจากโฟลเดอร์ assets จริงและมีตัวตรวจใน preflight
สองภาษาเหมือนส่วนอื่น — ระหว่างทำเจอรูรั่วในตัวตรวจคำแปล (มันอ่าน HTML จาก `index.html` ที่ hardcode ไว้) แก้แล้วและพิสูจน์ว่าล้มได้

**P2-2 · หลายแผนที่ต่อพื้นที่ (ชั้น/อาคาร)** — ✅ **เสร็จแล้ว**
พื้นที่หนึ่งเก็บได้หลายแผนที่ (ค่าเริ่มต้น 12 · `MAPS_PER_SPACE`) เข้าถึงได้จากประตูมิติที่ระบุแผนที่ปลายทาง, แถบเลือกชั้นในไซด์บาร์ หรือ `?m=` ใน URL
**ทุกคนอยู่ห้อง Colyseus เดียวกัน** — รายชื่อ, ข้อความส่วนตัว, กระดิ่งแจ้งเตือน และ "เรียกมาหา" ยังข้ามชั้นได้ เพราะคนที่อยู่ชั้นบนก็ยังอยู่ในพื้นที่นี้
สิ่งที่**ไม่**ข้ามคือเสียงและระยะ: แชทตามระยะ แชทห้อง และโซนส่วนตัว หยุดที่ขอบแผนที่ · รายชื่อบอกว่าใครอยู่ชั้นไหน และปุ่ม "ไปที่" พาข้ามชั้นไปยืนตรงที่เขาอยู่
ในเครื่องมือวาด: แท็บชั้นด้านบน เพิ่มชั้น สลับลำดับ และลบชั้น — ลำดับคือสิ่งที่กำหนดว่าคนเข้ามาเจอชั้นไหน จึงไม่ใช่การตกแต่ง
**โซนชื่อเดียวกันบนคนละชั้นคือคนละห้อง** — เป็นเหตุผลที่การตรวจชั้นอยู่ข้างการตรวจโซน ไม่ใช่อยู่ในนั้น
สลับแผนที่คือรีโหลด — ฉากอ่านโลกของมันครั้งเดียวตอน import การรื้อฉาก Phaser ที่รันอยู่ให้เป็นอีกแผนที่ใหญ่กว่าค่าของการเปลี่ยนชั้นมาก · ประตูมิติเฟดออกก่อนแล้วลงตรงช่องที่ระบุ
**ทดสอบ 56 ข้อ** (จาก 34) — ปิดกฎแยกชั้นแล้วล้ม 3 จาก 4 เคส และเคสที่ 4 (เดินลงมาแล้วได้ยินกัน) ยังผ่าน ซึ่งเป็นรูปร่างที่ตัวกันจริงควรเป็น

จองห้องประชุม, เชื่อม Google Calendar, เตือนก่อนประชุม

**P2-4 · บันทึกการประชุม** — `L`
ต้องตัดสินใจก่อนว่าอัดฝั่งเบราว์เซอร์ (ง่าย, ได้เฉพาะมุมคนกด) หรืออัดที่ SFU (ต้องรอ P0-2 ก่อน) รวมถึงเรื่องความยินยอมของผู้ถูกอัด

**P2-5 · เคาะประตู (Knock)** — ✅ **เสร็จแล้ว**
โซนส่วนตัวล็อกได้ (`locked` ในรูปแบบแผนที่ · สลับได้จากรายการโซนในเครื่องมือวาด) ห้องที่ล็อกจะเข้าได้ต่อเมื่อคนข้างในเปิดให้
**กฎอยู่ที่เซิร์ฟเวอร์ ตรงจุดที่มันมีความหมายจริง — การได้ยิน** ยืนอยู่ในห้องที่ล็อกโดยไม่ได้รับอนุญาตจะไม่ได้ยินอะไรและไม่มีใครได้ยิน เบราว์เซอร์ที่ถูกสั่งให้ไม่สนใจประตูจึงไม่ได้อะไรเพิ่ม
ฝั่งเบราว์เซอร์เป็นกำแพงนุ่ม: ช่องยังเดินได้ แต่ก้าวเข้าไปแล้วถูกดันกลับพร้อมการ์ดเคาะประตูอธิบายว่าทำไม — ทำ collision จริงรอบสี่เหลี่ยมที่มีประตูจะตีกับตัวหาเส้นทาง และคนที่เพิ่งได้รับอนุญาตกลางทางจะติดอยู่นอกห้องตัวเอง
**ห้องล็อกที่ไม่มีคนอยู่ ปล่อยให้คนแรกเดินเข้าได้** ประตูที่ล็อกโดยไม่มีใครอยู่หลังมันคือห้องที่ไม่มีใครเข้าได้เลย
การได้รับอนุญาตเป็นรายคน อยู่แค่ช่วงที่อยู่ในห้อง และถูกล้างเมื่อออกจากห้อง · เปิดประตูได้เฉพาะคนที่อยู่ในห้อง**และ**ได้รับอนุญาตแล้ว — การยืนอยู่ในห้องไม่ใช่การอยู่ในห้อง
การ์ดเคาะประตูใช้แผงเดียวกับการโบกมือ และเสนอ "ยังไม่สะดวก" ชัดเท่ากับ "เปิดให้เข้า" — ประตูที่เปิดได้อย่างเดียวไม่ใช่ประตู
**ทดสอบ 11 ข้อผ่านซ็อกเก็ตจริง** ปิดกฎแล้วล้ม 5 ข้อ

**P2-6 · แดชบอร์ดผู้ดูแล** — ✅ **เสร็จแล้ว**

game server บันทึกการเข้าออกด้วย**เครดิทที่เปิดประตูให้คนนั้น** เหมือนที่ประวัติแชททำ จึงไม่ต้องมีความลับใหม่ระหว่างสองเซอร์วิส และบันทึกการเข้าพื้นที่ที่ตัวเองเข้าไม่ได้ไม่ได้ · เวลาที่ใช้ในแต่ละโซนถูกสะสมทุกครั้งที่ย้ายห้องและส่งไปพร้อมตอนปิดรายการ
**รายการที่ยังไม่ปิดนับเป็นการเข้าใช้ แต่ไม่นับเป็นเวลาเลย** — มันคือคนที่ยังอยู่ หรือ session ที่เซิร์ฟเวอร์ทำหาย การเดาว่าเขาอยู่นานแค่ไหนคือการใส่ชั่วโมงที่ไม่มีจริงลงในรายงานที่คนใช้ตัดสินใจ · แดชบอร์ดบอกจำนวนที่ยังเปิดอยู่ตรง ๆ
เปิดให้เฉพาะเจ้าของและผู้ดูแล เพราะนี่คือ "ใครอยู่ที่ไหนนานเท่าไร" ซึ่งคนละเรื่องกับ "ใครออนไลน์" ที่ทุกคนเห็นได้
กราฟ 4 ชุด ทุกชุดเป็นซีรีส์เดียว จึงใช้สีเดียวและไม่มี legend — หัวข้อบอกอยู่แล้วว่าวาดอะไร · มีตารางตัวเลขใต้กราฟ เพราะกราฟไม่ใช่แหล่งอ้างอิง
กวาดทิ้งตาม `STATS_KEEP_DAYS` (ค่าเริ่มต้น 365 วัน)
**ทดสอบ 28 ข้อ** — ระหว่างทางเจอสองเรื่อง: วันถูกแบ่งด้วย UTC แต่ชั่วโมงใช้เวลาเซิร์ฟเวอร์ ตอนเย็นจึงตกไปอยู่ผิดวัน (แก้ให้ใช้นาฬิกาเดียวกัน) และเคส "รายการที่ยังไม่ปิด" ผ่านด้วยเหตุผลผิดเพราะเวลาเริ่มอยู่ในอนาคต

**P2-10 · ท่าทางอวตาร และสติกเกอร์บนแผนที่** — ✅ **เสร็จแล้ว**
เข้าจากปุ่มอิโมจิในแถบล่าง ซึ่งตอนนี้เปิดเป็นสามแถวมีหัวข้อ: **พูดออกไป · ท่าทาง · สติกเกอร์** — รีแอคชันที่หายไปกับสติกเกอร์ที่อยู่ต่อไม่ใช่ของอย่างเดียวกัน และไอคอนอย่างเดียวบอกไม่ได้
**ท่าทาง** (โบกมือ เต้น ปรบมือ ยกนิ้ว ฉลอง กำลังคิด) ส่งถึงทุกคนที่**มองเห็น**เรา ซึ่งเป็นวงกว้างกว่าคนที่ได้ยิน — โบกมือข้ามห้องคือจุดประสงค์ของการโบกมือ กฎระยะได้ยินจะกลืนมันหายไป · คนละแผนที่คือมองไม่เห็น จึงหยุดตรงนั้น · เครื่องหมายลอยขึ้นแล้วจาง พร้อมตัวละครขยับด้วย เพราะสัญลักษณ์ลอยเหนือคนที่ยืนนิ่งอ่านได้เป็นการแจ้งเตือน ไม่ใช่คนคนนั้นกำลังทำอะไร
**สติกเกอร์** อยู่ใน room state ไม่ใช่ข้อความ จึงยังอยู่ให้คนที่เดินผ่านมาอีกชั่วโมงเห็น ซึ่งเป็นเหตุผลเดียวที่จะวางมัน · อยู่รอดการรีโหลดของทุกเบราว์เซอร์ แต่ไม่รอดการรีสตาร์ทเซิร์ฟเวอร์ ซึ่งเป็นการแลกที่เหมาะกับของเล่น · เก็บคืนได้เฉพาะคนวาง กับเจ้าของพื้นที่ เพราะต้องมีใครสักคนเก็บของให้คนที่กลับบ้านไปแล้ว
ทั้งสองอย่างจำกัดด้วยรายการที่อนุญาตฝั่งเซิร์ฟเวอร์ เพราะทั้งคู่ถูกวาดในหน้าจอคนอื่น และช่องข้อความเปิดตรงนั้นคือช่องทางเขียนลงจอคนอื่น · จำกัดคนละ 12 ห้องละ 80 หมดอายุใน 4 ชม.
**ทดสอบ 17 ข้อผ่านซ็อกเก็ตจริง** ปิดกฎทีละข้อแล้วข้อที่คุมมันล้ม
ระหว่างทางเจอว่า `#emoji-pop` ถูกอ้างถึงทั้งใน CSS และใน scene แต่**ไม่เคยมีอยู่ใน markup** ปุ่มอิโมจิในแถบล่างจึงกดแล้วไม่เกิดอะไรมาตลอด

## ส่วนที่ 3 — ข้อจำกัดเชิงสถาปัตยกรรมที่ควรตัดสินใจก่อนลงมือ P1

เรื่องเหล่านี้ไม่ใช่ "ฟีเจอร์" แต่ถ้าตัดสินใจช้าจะต้องรื้องานที่ทำไปแล้ว

1. **P2P mesh กับ SFU** — ทุกฟีเจอร์เกี่ยวกับเสียง/ภาพ (บันทึกการประชุม, พื้นที่ส่วนตัว, ห้องใหญ่) ตั้งอยู่บนคำตอบข้อนี้ ควรตัดสินใจก่อนเขียนโค้ดสื่อสารเพิ่ม
2. **SQLite** — ตอนนี้ทั้งระบบอยู่บนไฟล์เดียว เขียนพร้อมกันได้ทีละราย ยังพอไหวสำหรับหลักสิบคน แต่ประวัติแชท (P0-4) และแดชบอร์ด (P2-6) จะเป็นตัวเร่งให้ต้องย้ายไป Postgres
3. **หนึ่งห้อง Colyseus ต่อหนึ่งพื้นที่** (`OfficeRoom` ตั้ง `autoDispose = false`) — แปลว่าทุกคนในพื้นที่อยู่ในโปรเซสเดียว ขยายข้ามเครื่องไม่ได้จนกว่าจะใส่ Redis presence
4. ~~**แผนที่อยู่ในโค้ดฝั่งเบราว์เซอร์**~~ — ✅ **ปิดแล้ว** พื้นที่หนึ่งเก็บแผนที่ของตัวเองในฐานข้อมูลได้ และเบราว์เซอร์โหลดมันตอนรัน  3 ธีมเดิมยังคอมไพล์ไปด้วยในฐานะแผนที่สำเร็จรูป ซึ่งเป็นสิ่งที่ควรเป็น — ที่หายไปคือข้อจำกัดว่าแผนที่*ต้อง*มาจากโค้ด

## ลำดับที่แนะนำ

```
สัปดาห์ 1     P0-3 (ใส่ค่า SMTP) + P0-1 (ตั้ง TURN บนเซิร์ฟเวอร์ แล้ว turn-check)
สัปดาห์ 3–4   P0-2 (SFU) — พร้อมทดสอบโหลดจริง 10+ คน  ⚠️ ต้องการเครื่องที่รับ UDP ได้เหมือน TURN
สัปดาห์ 5–6   P1-7 (มือถือ) — ข้อเดียวใน P1 ที่เหลือและไม่ติดโครงสร้างพื้นฐาน
              ·  P1-1 พื้นที่ส่วนตัว, P1-2 DM, P1-4 ตามตัว, P1-5 แจ้งเตือน, P1-6 ห้ามรบกวน, P1-8 โปรไฟล์ เสร็จแล้ว
สัปดาห์ 7–8   P1-3 (เชิญทางอีเมล) — รอค่า SMTP เท่านั้น
ต่อจากนั้น    P2-3 ปฏิทิน / P2-6 แดชบอร์ด เป็นสายงานหลัก, P1-7 มือถือ เป็นสายงานคู่ขนาน
```

เหตุผลของลำดับนี้: **P0 ทุกข้อคือสิ่งที่ทำให้ผู้ใช้เจอปัญหาโดยที่เราไม่รู้ตัว** (เสียงไม่ติดเพราะไม่มี TURN, ข้อความหาย, อีเมลไม่ถึง) ส่วน P1 คือสิ่งที่ผู้ใช้จะบอกเราเองว่าขาด และ P2 คือสิ่งที่ตัดสินว่าเราขายเป็นสินค้าได้หรือทำได้แค่พื้นที่เดียวให้ทีมเดียว
